Performance ​

The shared CPU engine and its threads ​

All tenferro-rs operations of a process run on one shared CPU execution engine. The engine keeps its buffer pool, which recycles output allocations, and its kernel plan cache between calls and across contexts. Calls from different contexts and Julia threads take turns on it.

By default the engine is serial. To run kernels on a worker pool, set the TENFERRO_NUM_THREADS environment variable before the first tensor operation, or call Tenferro.set_num_threads at any time:

julia
using Tenferro
Tenferro.set_num_threads(4)   # rebuilds the engine with 4 workers
Tenferro.num_threads()        # 4

Changing the thread count rebuilds the engine, so its buffer pool and plan cache start empty. Tensors and contexts created before the change remain valid. Threaded kernels may sum in a different order than serial ones, so results can differ in the last bits. The default stays serial so that results are reproducible and the engine does not compete with Julia or BLAS threads.

Reusing derivative programs ​

All eager contexts share one tenferro-rs eager runtime. Its caches of compiled derivative programs and AD transforms persist across contexts and DifferentiationInterface calls, and tenferro-ad bounds them at 128 entries and 64 MiB each. The cache key is the structure of the recorded computation and the shapes and element types of its inputs, not their values. A second gradient call on the same function with new data of the same shapes therefore reuses the compiled reverse pass, even when the function is a new closure.

Each DifferentiationInterface call closes its context before it returns, which frees the tenferro-rs graph at once. Contexts left for Julia's garbage collector would stay registered in the shared runtime, and every reverse pass scans the tensors of all live contexts, so steps would get slower until a collection runs.

Gradients, and each seed of a pullback, are computed for all inputs in one reverse pass. On the traced backend, the value and all gradients are compiled and run as one program. A TracedContext keeps the value of every node it has evaluated until it is closed, so reading a value again does not recompile.

Arrays and numbers that are mixed into tensor operations, Tenferro.constant values and DifferentiationInterface.Constant data are untracked constants. No gradient is computed for them, and they do not take part in reverse passes.

Dense layers and cross-entropy ​

A dense layer composed from tensor operations is a dot_general, a bias broadcast, an add and an activation, and its derivative adds several more instructions. With a fixed cost per operation and instruction, a small model spends more time in that bookkeeping than in its kernels. Tenferro.dense(σ, W, x, b) runs σ.(W * x .+ b) as one native operation for identity and relu with Float32 or Float64 operands, and its pullback is one native operation per layer. Tenferro.logitcrossentropy(ŷ, y; agg) does the same for the softmax cross-entropy of logits. TenferroLux routes Lux.Dense, LuxLib's fused_dense_bias_activation and CrossEntropyLoss(; logits=Val(true)) to them.

The matrix products of the native dense kernels call Julia's BLAS through libblastrampoline (sgemm_64_/dgemm_64_), so they use the BLAS library and the BLAS.set_num_threads setting of the Julia session, not Tenferro's worker pool. Tenferro registers these entry points when it loads; without them the kernels use a built-in GEMM (faer) on the calling thread.

Crossing the Julia boundary ​

EagerTensor(ctx, x), TracedTensor(ctx, x) and Array(t) copy numeric data with one memcpy in each direction; only Bool data is converted element by element. Eager gradients are copied straight from tenferro-rs's gradient slot into the Julia result, without wrapping them in a tensor first, and the unit seed of a scalar gradient is made on the Rust side.

The Rust library keeps recently freed blocks of 32 KiB to 64 MiB, up to 64 blocks and 256 MiB in total, and hands them out again for requests of the same rounded size. A training step allocates and frees buffers of the same sizes every time. Without the cache, the system allocator returns their pages to the OS, and the next step pays page faults to touch them again.

Where the time goes ​

Each Tenferro operation crosses into Rust. A call that only adds a graph node costs about 11–12 µs, almost all of it on the Rust side: semantic recording and runtime bookkeeping. The RustCall boundary itself costs about 1 µs. Models with many small operations are therefore limited by the number of operations, not by kernel time.
